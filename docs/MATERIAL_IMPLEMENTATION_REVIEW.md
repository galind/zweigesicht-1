## Source and runtime findings

Reviewed `materials.ts`, `SurfaceOcclusion.ts`, and the material/contact-pass integration in `MovementViewer.ts`, together with the installed Three.js r186 `SSAOPass`, `SSAOShader`, render-pass and material behavior. The earlier controller review remains in `IMPLEMENTATION_REVIEW.md`; method names here avoid unstable formatting-dependent line references.

- **Geometry and placements preserved.** `createMaterial` computes a bounding-box cache and reads component-local positions/normals. Its shader hook varies color, roughness and shading normals; it adds no displacement, vertex transformation, geometry replacement, triangulation or normal-buffer edits. `ingest` retains the manifest world matrix and reusable definition geometry. The new harness hashes every decoded attribute, morph-attribute and index buffer before ingest, then compares all 339 decoded geometry objects after material creation, reveals, timing, return and catalog ingest. All bytes match. The count includes separately decoded overview and catalog copies, not 339 unique CAD definitions. Existing checks still prove 222 movement meshes sharing 138 geometries, 364 total catalog meshes, unchanged existing movement object identities, and zero assembled-matrix error.
- **Surface coordinates travel with the component.** `vFinishPosition=position` and `vFinishNormal=normal` use local mesh coordinates. The bounding-box-derived origin/shortest axis therefore remain attached during rigid source-preserving transformations. The common shader program key is appropriate because source code is shared and origin, axis, pattern and enable values are uniforms. `setFinishEnabled` changes a retained per-material uniform without generating a new material or shader program. Function treatment, selected parts and subdued context turn this procedural treatment off in `retargetVisibility`.
- **Contact depth units match source millimetres.** `SurfaceOcclusion.render` refreshes projection/inverse projection and near/far uniforms every rendered frame. The installed shader compares normalized linear depth, so dividing 0.035 mm and 1.4 mm by `far - near` is consistent with the source-unit camera. The 0.8 kernel radius operates in view-space source units. The 0.48 strength substitution matches the installed shader source and is asserted in the harness.
- **Pass ordering and state are clean.** `tick` renders beauty first, then the contact pass for Finish unless quality is Low. The real installed pass renders mesh normals/depth, SSAO, blur and final multiplicative composition to the default framebuffer. Its input/output buffer parameters are unused in this default screen-output mode, so the wrapper's repeated target argument does not create framebuffer feedback. A CPU renderer facade verifies this four-stage sequence, temporary line hiding/restoration, null scene override afterward, clear color/alpha and autoClear restoration, and the final default framebuffer. No postprocessing target remains bound for the next beauty frame. No contact work is added to an otherwise idle paused frame.
- **Resource ownership is explicit.** `SurfaceOcclusion.dispose` releases its noise texture and SSAO material before upstream disposal. Those two resources are omitted by the installed `SSAOPass.dispose`; the explicit calls are needed and do not duplicate upstream cleanup. The harness observes exactly one disposal event for each of ten pass-owned targets, materials, noise texture and fullscreen geometry. `MovementViewer.dispose` invokes that cleanup alongside its existing scene, environment and renderer cleanup. Resize reuses targets; revealing, selecting and switching treatment reuse materials.
- **Context restoration preserves the environment assignment.** The actual `onContextRestored` handler still regenerates PMREM, disposes the old target and temporary generator/room, reconnects the replacement texture, and requests rendering without modifying geometry. The CPU handler test remains passing. Contact targets are rendered afresh after restoration; actual restored shader output and GPU resources require browser evidence.

The new diagnostic `triangles` and `drawCalls` deliberately record the beauty pass before SSAO overwrites `renderer.info.render`. They remain useful geometry/visibility counters, but **do not represent total GPU work**: contact rendering adds a mesh normal/depth pass and three fullscreen passes. Performance reports must use actual frame measurements and identify whether `contactShading` was enabled. A higher steady resource count after adding the pass is expected, rather than a leak by itself.

## Evidence and limits

`node scripts/cad/review-runtime.mjs` passes 14/14 on the reviewed source. The geometry and controller checks use actual prepared local GLBs, actual decoded buffers and actual application methods. The contact-pass check constructs the real installed SSAOPass and uses a CPU renderer facade; the PMREM handler uses CPU stubs. Neither test compiles GLSL, allocates a real framebuffer, renders pixels or proves physical-device performance.

The lead's separately produced `artifacts/browser/materials-interactions.json` was inspected: all six real-browser checks pass, including 20 interrupted reveals, uncover reversal, exact source return, separation pausing playback, stable 138 GPU geometries / 7 textures through switches, and zero additional idle renders. Its eight timing samples are not a sustained performance qualification. Current visual artifacts include `materials-assembled.png` and `materials-closeup.png`; visual/shader, sustained performance and context-loss QA are owned by the lead and must be reported from those actual runs.

Earlier `context-restored.png/json` and `benchmark-5min.json` demonstrate the prior implementation's reflection recovery and 18,000-frame stability. They predate this contact/material refinement and are not substitutes for checking the changed renderer. Do not carry forward the old 137-geometries / 2-textures baseline as this pass's resource budget.

Exact definition families resolve the known broad-regex errors documented in `MATERIAL_REFERENCE_AUDIT.md`. Colors, roughness, grain scale/direction, face-versus-edge treatment, lighting and contact strength remain authored interpretations. The shader brightens existing edge/chamfer geometry; it does not restore missing source faces or establish measured bevels. Source exceptions, variant decisions, mechanical contact approval, actual-phone/thermal qualification, human comprehension and publication/redistribution permissions remain separate gates. The current source review supports local visual engineering review within those limits.
